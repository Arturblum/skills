# Rewrite issue after check

`issue-check` found where the issue and the code diverge. This skill carries those findings into the issue, so the next reader starts from a description that is true, and sees which decisions are still open.

The issue is shared and the edit is outward-facing: the reader approves the rewrite before it is written.

## Process

1. **Get the findings.** Use the `issue-check` report from this conversation: the claims marked _stale_ or _wrong_, the decisions buried in comments, the missing acceptance criteria, the blockers, the verdict. With no report in context, call the Skill tool with `issue-check` first.
   - Verdict **not relevant** (done, superseded, obsolete): stop. A rewrite would polish an issue that should close; say so and leave closing to the reader.

   Done when every finding has a number and a kind: fix, decision made, missing criterion, blocker, or open choice.

2. **Draft the new description.** Start from the current body, fetched fresh (`gh issue view <n> --json body,title`), and change only what a finding requires. Keep the author's structure, headings and wording wherever the claim _holds_.
   - **Fixes**: replace each stale or wrong claim with the verified fact, citing `path:line` or the ADR.
   - **Decisions made**: fold each decision that lives only in a comment into the body, with a link to the comment.
   - **Missing criteria and scope**: add the acceptance criteria and scope changes the findings call for.
   - **Blockers**: list them under "Blocked by" with links. Where GitHub's native dependency is missing, say so in the report, because the edit that adds it is the reader's call.
   - **Open decisions**: one section, `## Open decisions`, in the issue's own language. Each entry holds the question in plain words, the options with what each costs, the recommendation, and the code or ADR that bears on it. Record each as _open_: the rewrite states the choice and leaves it for the decider.

   Done when every finding from step 1 has a place in the draft, and every sentence left unchanged is a claim that _holds_.

3. **Show before applying.** Present the changes as a before/after of each changed passage, then the full new `## Open decisions` section, then the comment you will post. Ask for approval.
   Done when the reader has said yes. Edits requested are applied and shown again.

4. **Apply.**
   1. Save the current body to a file outside the repo, so the old text is one command away.
   2. `gh issue edit <n> --body-file <file>`. GitHub also keeps the issue's edit history.
   3. Post one comment (`gh issue comment <n> --body-file <file>`), opening with `> *This was generated by AI during an issue check.*`, listing what changed and why in a few bullets, and linking the open decisions.
   Titles, labels, assignees and state stay as they are; changing them is a separate request.

5. **Verify.** Re-read the issue with `gh issue view <n> --comments`. Done when the body matches the approved draft and the comment is posted. Report the issue link, and the path of the saved old body.
